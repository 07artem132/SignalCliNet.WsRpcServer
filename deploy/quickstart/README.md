# Свій шлюз сповіщень Signal однією командою

Піднімає власний шлюз для модуля сповіщень Потужності (і будь-якого іншого клієнта WS JSON-RPC):
signal-cli + `SignalCliNet.WsRpcServer` + Caddy з сертифікатом Let's Encrypt. Номер Signal на сервері —
спільний бот команди; люди в команді шлють через нього в прив'язані Signal-групи.

```bash
curl -fsSL https://raw.githubusercontent.com/07artem132/SignalCliNet.WsRpcServer/main/deploy/quickstart/install.sh \
  | sudo bash -s -- --domain notify.example.com --extension-id <ID розширення> --team "Назва команди"
```

Скрипт ставить Docker (якщо нема), збирає образ із готового релізу, показує QR для прив'язки номера,
запускає стек і друкує адресу шлюзу та одноразовий інвайт для першого team-admin. Повторний запуск
безпечний: прив'язаний номер і наявна команда не чіпаються, лише видається новий інвайт.

## Що потрібно заздалегідь

| Що | Навіщо |
|---|---|
| Linux-сервер x64 або arm64 з публічним IP, від 1 GB RAM (з запасом — 2 GB) | у контейнері працюють JVM signal-cli і .NET-шлюз; без привʼязаного номера стек займає ~250 MB, з ботом JVM росте |
| Домен (або піддомен), A/AAAA-запис якого вже вказує на сервер | Caddy отримує сертифікат Let's Encrypt; без валідного TLS браузер не підключиться |
| Відкриті вхідні порти **80** і **443** | 80 — перевірка домену Let's Encrypt, 443 — `wss://` для клієнтів |
| Телефон з активним Signal на номері для бота | сервер стає *привʼязаним пристроєм* цього номера. Краще окремий номер, не особистий |
| ID розширення Потужності | `chrome://extensions` → увімкни «Режим розробника» → картка Потужності → рядок **ID** (32 літери a–p) |

Решта (.NET, Java 25, signal-cli, сертифікати, ключі) — всередині образу або генерується на першому старті.

## Що відбувається під час встановлення

1. **Docker.** Якщо його нема — ставиться офіційним `get.docker.com`.
2. **Файли стека** лягають у `/opt/signal-notify` (`--dir`): `compose.yml`, `Dockerfile`, `Caddyfile`,
   `.env` (домен і версія) та `gateway.json` (налаштування шлюзу).
3. **Образ.** `Dockerfile` качає all-in-one бандл останнього релізу (`linux-<arch>-bundle`: сервер + JRE 25 +
   signal-cli) і звіряє SHA-256 із `SHA256SUMS` того ж релізу. Ні .NET SDK, ні токен GitHub не потрібні.
4. **Привʼязка номера.** У терміналі з'являється QR. На телефоні: Signal → *Налаштування → Привʼязані
   пристрої → «+»* → скануй. QR живе ~2 хв; не встиг — запусти команду ще раз.
5. **Старт.** Шлюз генерує на томі CA, сертифікати, admin-ключ і пеппери (`/data/secrets`, права `0600`),
   Caddy отримує сертифікат для домену.
6. **Команда й інвайт** (з `--team`): створюється команда і одноразовий інвайт з роллю `team-admin`
   (дійсний добу).

Наприкінці скрипт друкує:

```
  Адреса для розширення:  wss://notify.example.com
  Номер бота:             +380XXXXXXXXX
  Дозволені Origin:       chrome-extension://<id>
  Інвайт team-admin для «Назва команди» (одноразовий, до …):
      K7QT-9F2M-4XZP-…
```

## Після запуску

1. **Інвайт — особисто.** Передай код team-admin поза ботом (особисто або в уже довіреному каналі). Це
   секрет: хто погасить його першим, той і стане team-admin.
2. **Team-admin підключає Потужність:** у налаштуваннях модуля сповіщень вводить адресу `wss://<домен>`,
   номер бота (`+380…`) і код інвайту. Розширення реєструє ключ пристрою, далі входить без коду.
3. **Бот у групах.** Додай номер бота в Signal-групи, куди мають іти сповіщення.
4. **Прив'язка груп до псевдонімів.** Team-admin у модулі просить код для псевдоніма (`all`, `admin`,
   `dir:<id>`, `login:<id>`) і вставляє його повідомленням у потрібну групу. Бот бачить код і прив'язує
   групу. Прив'язка живе 30 днів, потім її повторюють.
5. **Решта команди:** team-admin видає багаторазові інвайти у свою команду з модуля
   (`createTeamInvite`); кожен пристрій погашає код один раз.

Модель команд, ролей і псевдонімів детально: [`docs/shared-bot.md`](../../docs/shared-bot.md#команди-й-сповіщення-за-alias-зміна-add-team-notify).

## Керування

Admin-порт шлюзу (mTLS) слухає лише loopback усередині контейнера, тому команди йдуть через
`docker compose exec`:

```bash
cd /opt/signal-notify
docker compose exec wsrpcserver wsrpc-admin ping
docker compose exec wsrpcserver wsrpc-admin accounts                    # номер бота
docker compose exec wsrpcserver wsrpc-admin teams                       # команди, к-сть учасників і team-admin
docker compose exec wsrpcserver wsrpc-admin create-team "Друга команда"
docker compose exec wsrpcserver wsrpc-admin invite --team <teamId> --role team-admin
docker compose exec wsrpcserver wsrpc-admin set-role <identityId> team-admin
docker compose exec wsrpcserver wsrpc-admin revoke <identityId>         # втрачений/скомпрометований пристрій
```

Якщо команда лишилась без team-admin (`teams` показує `activeTeamAdmins: 0`), видай новий інвайт
`--role team-admin` у ту ж команду.

### Origin розширення та інші налаштування

`gateway.json` монтується в контейнер як `appsettings.Production.json`. Дефолт від скрипта:

```json
{
  "Server": {
    "Auth": {
      "Enabled": true,
      "AllowedOrigins": ["chrome-extension://<id>"],
      "MaxUnauthenticatedPerIp": 64
    },
    "Admission": { "Enabled": true },
    "GroupClaim": { "Enabled": true }
  }
}
```

- `AllowedOrigins` — точний збіг, без `/` в кінці. Порожній список відхиляє будь-який браузер (`HTTP 403`).
  Інший ID розширення (dev-збірка, інший браузер) — додай ще один рядок. Простіше: запусти `install.sh`
  ще раз з `--extension-id` (кілька — через кому), старий файл збережеться як `gateway.json.bak`.
- `MaxUnauthenticatedPerIp: 64` — за проксі всі клієнти приходять з IP Caddy, тож дефолтні 8 одночасних
  неавтентифікованих конектів ділились би на всю команду.
- Усі ключі (ліміти, TTL токенів, coalescing) — у [`docs/self-host.md`](../../docs/self-host.md#конфігурація-appsettingsjson).

Після зміни: `docker compose up -d`.

## Оновлення

```bash
cd /opt/signal-notify
sed -i 's/^WSRPC_VERSION=.*/WSRPC_VERSION=2.4.0/' .env   # або: install.sh … --version 2.4.0
docker compose up -d --build
```

Це коротке вікно простою: шлюз працює в одному екземплярі на томі (другий не стартує), тож старий
контейнер зупиняється перед запуском нового. Стор мігрує схему автоматично.

## Бекап

Том `signal-notify_gateway-data` — це і є бот: привʼязаний пристрій Signal, SQLite-стор (команди, пристрої,
прив'язки груп) і секрети. Втрата тому = нова прив'язка номера й новий онбординг усіх пристроїв.

```bash
cd /opt/signal-notify
docker compose stop wsrpcserver
docker run --rm -v signal-notify_gateway-data:/data -v "$PWD":/backup debian:bookworm-slim \
  tar czf /backup/gateway-$(date +%F).tgz -C /data .
docker compose start wsrpcserver
```

Архів містить приватні ключі: зберігай його на шифрованому носії. Сам диск сервера теж має бути
шифрованим (шифрування диска провайдера або dm-crypt).

## Безпека

- Назовні відкриті лише 80 і 443 (Caddy). Порт шлюзу 9000 і admin-порт 9443 на хост не публікуються.
  На фаєрволі сервера чи в Security Group провайдера залиш вхідні 22, 80, 443.
- Admin-ключ (`/data/secrets/admin-client.key`) не покидає тому; скрипт його не друкує.
- Клієнти автентифікуються токеном і ключем пристрою (ECDSA P-256, PoP); нових користувачів пускає лише
  інвайт. Текст повідомлень шлюз бачить (наскрізного шифрування між клієнтом і ботом немає), тож сервером
  має керувати людина з відповідним допуском.
- Core dump-и для контейнера шлюзу вимкнено, щоб дамп не виніс ключі на диск.

## Якщо щось не так

| Симптом | Причина → що робити |
|---|---|
| `Увага: <домен> поки не резолвиться` | DNS ще не оновився → дочекайся й перезапусти `docker compose restart caddy` |
| Розширення: помилка TLS / сертифіката | Caddy не отримав сертифікат: закриті 80/443 або DNS не на цей сервер → `docker compose logs caddy` |
| Розширення: `HTTP 403` на підключенні | ID розширення не в `AllowedOrigins` → див. «Origin розширення» |
| `Link request error` або QR протух | Повтори `install.sh` (номер ще не привʼязаний — покаже новий QR) |
| `шлюз не відповів за 3 хв` | `docker compose logs wsrpcserver`; найчастіше — мало RAM або том зайнятий іншим екземпляром |
| `Помилка сервера -32006` при вході з інвайтом | інвайт прострочений, уже погашений або вичерпано спроби → видай новий |
| Сповіщення в групу: `-32007` | групу не прив'язано до цього псевдоніма, або людина, що вставила код, вийшла з групи → прив'яжи знову |

## Без домену

Let's Encrypt видає сертифікат лише на домен. Варіанти:

- безкоштовний піддомен (DuckDNS тощо), A-запис → IP сервера, далі як звичайно;
- внутрішній CA шлюзу без домену — стек у [`deploy/docker-compose.yml`](../docker-compose.yml): тоді
  `ca.crt` шлюзу треба додати в довірені на кожному комп'ютері з розширенням
  ([`deploy/DEPLOYMENT.md`](../DEPLOYMENT.md) §4).
