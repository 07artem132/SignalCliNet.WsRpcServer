# Спільний бот: інвайт-гейт та abuse-лог

Цей документ описує анти-abuse-модель багатокористувацького («спільного бота») режиму
`SignalCliNet.WsRpcServer` (зміна `add-invites-admin`): як обмежується онбординг identity (інвайти)
і як фіксуються security-релевантні події (abuse-лог) без витоку PII.

> **Скоуп.** Тут — секція «Інвайти + abuse-log» (tasks 1.x, 3.3). Admin-bootstrap, mTLS та
> tamper-evident **audit-trail** (окремий від abuse-логу лог з hash-chain) — окрема секція
> (див. `openspec/changes/add-invites-admin`).

## Інвайт-гейт (Sybil-захист онбордингу)

Створити нову identity можна ЛИШЕ погасивши one-time інвайт-код (`redeemInvite`). Це Sybil-гейт:
без валідного інвайта у спільного бота не з'являються нові користувачі.

**Код.** ≥96-bit CSPRNG (реалізація: 128-bit / 16 байт) у Crockford-base32 (алфавіт без `I/L/O/U`,
щоб не плутати з `1/0`), розбитий дефісами на блоки по 4 для ручного вводу
(напр. `K7QT-9F2M-4XZP-…-ZC`). Нормалізація перед lookup: upper-invariant, прибирання
роздільників/пробілів і фолд сплутуваних символів (`O→0`, `I/L→1`), тож дрібні помилки ручного
вводу не ламають гашення.

**At-rest.** У БД лежить лише `code_hash = base64(SHA-256(нормалізований код))` — НЕ сам код.
SHA-256 (а не HMAC) обрано свідомо: код сам є високоентропійним 128-bit секретом, тож хеш потрібен
лише для lookup/at-rest-приховування, а не для секретності (щоб «вгадати» рядок за хешем, треба
вгадати 128-bit код). Окремого invite-пеппера у деплої немає, а reuse `pepper_abuse` сплутав би
домени.

**Attempt cap (G12).** Кожен інвайт має `max_attempts`. Кожна спроба редемпшну (зокрема невдала)
АТОМАРНО інкрементує `attempt_count` у тій самій транзакції, що й перевірка/consume — тож паралельні
guesses не обходять cap гонкою. Понад cap → відмова.

**Atomic consume (W20).** Успішний редемпшн виставляє `consumed=1` + `consumed_by` умовним
`UPDATE … WHERE consumed=0` у одній транзакції: з паралельних редемпшнів одного коду виграє РІВНО
один; решта отримують відмову.

**Anti-oracle.** Невідомий / прострочений / уже погашений / понад-cap код повертають ІДЕНТИЧНУ
помилку `-32006` — клієнт не дізнається причину невдачі.

**М'який глобальний rate-cap (task 1.2).** Понад цим — soft глобальний ліміт спроб редемпшну
(дефолт 20/хв, монотонне ковзне вікно). Він **м'який** навмисно: перевищення дає лише ТИМЧАСОВУ
відмову (`-32005` з `retry_after`), що самоочищається зі зсувом вікна — НЕ бан. Жорсткий глобальний
cap перетворив би анти-brute-force-контроль на важіль **shared-fate DoS** (один зловмисник вичерпав
би спільний бюджет і заблокував онбординг усім). Справжня стійкість до підбору — у per-code cap +
128-bit ентропії коду; вікно лише зрізає пікову частоту.

## Регламент передачі коду користувачу (task 1.2)

Інвайт-код — високоентропійний секрет. Правила поводження:

- **Out-of-band доставка.** Адмін передає код користувачу поза самим ботом (особисто / у вже
  довіреному каналі). Плейнтекст-код повертається емітенту з `Create` **рівно один раз** і НІКОЛИ
  не логується та не зберігається (у БД лише `code_hash`).
- **Один код — один користувач.** Кожен інвайт one-time (`consumed` після першого успішного
  редемпшну). Не роздавати той самий код кільком людям.
- **Короткий TTL.** Видавати з мінімально достатнім TTL — прострочений код не редемиться (anti-oracle
  однаково з рештою причин).
- **Не в логи / не в чати.** Код не можна пересилати через сам бот-акаунт чи будь-який лог; витік коду
  = потенційна нова identity, доки код не погашено/не прострочено.
- **Компрометація.** Якщо код міг витекти — вважати його спаленим; видати новий (окремий інвайт).
  Персистентного «відкликання» окремого коду поки немає (наявний важіль — TTL + one-time consume);
  admin-керування інвайтами приходить із секцією 2 (`createInvite`/список/revoke).

## Abuse-лог (shared-bot події)

Security-релевантні події спільного бота (напр. `invite_redeemed`) фіксуються у таблиці `abuse_log`.
Сирий суб'єкт (code hash, номери тощо) **ніколи** не зберігається у відкритому вигляді й не логується
(privacy contract). Замість нього — домен-розділений HMAC:

```
subject_hmac = base64( HMAC-SHA256( pepper_abuse, salt ‖ callerIdentityId ‖ subject ) )
```

- `pepper_abuse` — домен-розділений ключ (окремий від token-пеппера), той самий домен «abuse», що й
  new-recipient tracker.
- `salt` — **per-record** CSPRNG (128-bit), зберігається поруч із записом.
- pre-image містить `salt` І `callerIdentityId` (NUL-розділені) — це закриває **W24**
  (equality-oracle): той самий суб'єкт, залогований різними записами або різними акторами, дає РІЗНІ
  hmac, тож спостерігач лог-таблиці не може звірити рівність суб'єктів між записами.

## Abuse-лог vs audit-trail (два різні логи)

Abuse-лог сам по собі **не** tamper-evident: без hash-chain запис у адмін-БД можна відредагувати або
видалити без сліду. Тому shared-bot має **два окремі** логи з різними цілями:

- **Abuse-лог** (`abuse_log`, ця секція) — обсяг-throttle domain: W24-HMAC приховує суб'єкта й ламає
  equality-oracle. Операційний сигнал, не криптографічний доказ. Редагування записів невиявне.
- **Audit-trail** (`audit_log`, секція 2, M8) — security-домен: **tamper-evident hash-chain**. Кожен
  запис зобов'язується до попереднього
  (`entry_hash = SHA-256(prev_hash ‖ seq ‖ event_type ‖ actor ‖ detail_hash ‖ logged_at)`, genesis =
  нулі), тож підробка/видалення будь-якого запису рве ланцюг (`AuditLogService.VerifyChain()` → `false`).
  Зберігається лише `detail_hash` (SHA-256 деталей) — жодних токенів/номерів у тілі. Події:
  лінк бот-девайсу (redeem інвайту), видача інвайту (admin `createInvite`), revoke identity,
  admin `listAccounts(all)`.

**Резолюція residual секції 1:** tamper-evident audit-trail **реалізовано** у секції 2 (`AuditLogService`
+ міграція `audit_log` v5). Для security-подій, де потрібна доказовість у ворожому середовищі, покладайся
на audit-trail (hash-chain), а не на abuse-лог. Abuse-лог лишається окремим операційним сигналом для
обсяг-контролю.
